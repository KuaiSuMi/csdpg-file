# 三项学术基线：选型、复现与项目接入

历史实验说明：本文保留旧 feTruth/Kivi/Reynard 流程。当前学术基线为 **Infer/Pulse + feTruth**，请使用[最新学术指南](两项学术基线复现.md)和[当前选型](学术基线复审结论.md)。

当前选择以最新复审为准，以下的三项组合和判断仅记录当时实验。

## 1. 先把项目要解决的问题说清楚

设想一个下单系统：订单服务检查库存，再调用支付服务，最后返回订单结果。用户看到的是一次请求，背后涉及代码、部署和服务调用三部分。

代码里，创建订单的方法可能承担了过多支付逻辑；部署时，扩容规则和副本分布规则可能相互冲突；运行时，推荐服务出错可能连带使整个页面失败。这些问题的输入和判断方法不同。

当前项目要做两件相连的工作：

1. 读取源码、部署信息和运行记录，整理出后续程序能够处理的中间结构。例如“哪个类调用哪个类”“哪个服务由哪个 Deployment 部署”“哪个检查在什么输入下失败”。
2. 利用问题证据提出修改，再检查修改是否解决原问题、是否破坏原来允许的行为。

现有 Semgrep、Java CFG Builder、SCIP、Radon 等能力已经能提供静态事实。它们的角色主要是收集和分析源码。现在需要补入可以比较的既有诊断方法，并建立修改前后的判定办法。

这里几个词的意思如下：

| 词 | 在本项目里的意思 | 一个具体例子 |
| --- | --- | --- |
| baseline，基线 | 已有方法，作为项目新方法的比较对象 | 用 feTruth 的方法移动建议，与项目自己的诊断结果比较 |
| benchmark，评测集 | 一组输入、已知问题、预期行为和判定程序 | 推荐服务故障后，页面仍应返回 200，并用空列表表示暂无推荐 |
| 复现 | 运行作者的方法，记录版本、输入、命令和原始输出 | 运行 Kivi 作者的 C3 案例，保存 SPIN 的反例和检查日志 |
| 适配 | 将原工具输入输出接到当前项目 | 把 Kivi 的调度检查结果挂到图谱 Deployment 节点上 |
| oracle，判定准则 | 决定一次执行是否正确的规则 | 检查 HTTP 状态码及返回内容，而不只检查进程是否退出 |

本次没有定义新的“成熟度总分”。方法移动候选、模型检查结果和业务测试结果不能直接相加。三项基线分别回答三个问题，最后通过共同的对象身份和证据结构关联。

## 3. 学术基线的选择理由

三项方法分别覆盖源码职责、配置约束和故障下的业务行为。以下解释历史复现的价值，不表示它们都满足新准入要求。正式发表不能代替实际易用性，输入互补也不能替代通用性。

### 三项方法的用途与准入限制

**选择 feTruth，是为了把已经采到的类依赖用于一个明确的设计诊断任务。** 它给出源方法、源类和目标类，便于接到现有 Java 类节点，也便于人工核查。代价是范围窄：它主要处理 Feature Envy，不能代替所有代码质量检查；公开实现也不提供 Python 同等能力。

**选择 Kivi，是因为项目正在从云厂商数据源转向本地 K8s。** 这时有价值的问题不只是“某个字段有没有填写”，还包括“扩容、调度和放置约束能否共同工作”。Kivi 给出违反性质的执行路径，适合构造部署问题样例及修改前后的模型对照。代价是需要明确建模范围，当前不能把任意集群对象原样丢进去就宣称完成验证。

**保留 Reynard，是因为项目不仅要指出问题，还要判断修改后的服务行为。** 运行期故障测试能检查静态结构和部署配置之外的实际结果。它适合与 otel-demo 的服务调用、观测和故障注入原型衔接。代价是必须接入代理，并事先给出业务允许的结果；工具本身不知道“推荐可以降级、扣款不能重复”这样的业务约束。

按新要求，Kivi 的现成 intent 不等于能够直接验证任意集群：官方称实际输入解析器为 preliminary，仍需核对支持对象与模型输入。Reynard 自动生成的是故障组合，业务请求和正确性断言由使用方提供，因此作为验证工具保留。feTruth 不需要逐项目编写规则，但旧依赖、模型准备和单一异味范围必须明确，不能仅凭有一条命令就认定安装与使用都简单。

三者的互补关系是选型判断，不是已经通过一个共同排行榜证明的优胜结论。

## 4. feTruth：判断一个方法是否放错了类

### 4.1 从一个简单例子理解 Feature Envy

假设 OrderService 中有一个方法，几乎所有操作都在读取 PaymentService 的字段和调用 PaymentService 的功能，很少使用 OrderService 自己的状态。这个方法可能更适合放进 PaymentService。设计领域把这种过度依赖别的类的现象称为 Feature Envy，常译为“依恋情结”。

但“调用了支付服务”本身不是问题。订单服务本来就需要组织库存和支付操作。一个合理的业务编排方法也可能大量调用别的服务，所以工具建议必须结合职责和行为核对。

feTruth 的方法可以分为四步：

1. 从真实项目重构历史中收集方法移动样例，清理不能代表设计问题的样例。论文结合启发式规则和决策树改善训练数据。
2. 对源方法和候选目标类提取特征，包括名称信息和结构耦合信息。作者代码中的 dist、cbmc、mcmc 用于表达方法与类之间的关系。
3. 使用词向量处理标识符，并把结构特征交给训练好的深度模型，判断某个方法与目标类的组合。
4. 按阈值筛选，输出 Move Method 建议：源方法是谁、目标类是谁。

这里没有使用大语言模型，也没有在本项目重新训练网络。0.95 是当前作者程序的筛选阈值，不能解释成“该建议有 95% 的正确概率”。方法细节依据[论文](../references/papers/fetruth-fse2023.pdf)及[作者实现](https://github.com/lyoubo/feTruth)。

### 4.2 为什么要分开两种复现

作者论文归档与后来的源码输入流程并不完全相同。本次分别记录，防止把“某个归档样例一致”扩展成“所有新项目输出都已验证”。

| 实验 | 固定版本与输入 | 实际结果 | 能支持的结论 |
| --- | --- | --- | --- |
| 论文归档推理 | v1.0.0，提交 a896445；使用作者已提取好的 jsoup 特征 | 输出 16 条，与作者保存的 16 条逐项一致 | 这一份归档输入上的推理结果重放成功 |
| 当前项目源码分析 | 提交 b4f8d5c；输入 maturity-evaluate 自带 java_app 的 4 个 Java 类 | 提取 1 个候选方法、2 个方法/目标类组合，输出 1 条建议 | 作者较新源码流程能够读入本项目 Java 示例并给出结果 |
| 模型差异诊断 | 对同一份已有测试特征切换仓库中的模型文件 | implementation 模型输出 152 条，根目录模型输出 0 条，作者保存示例为 15 条 | 这些模型和保存结果存在差异，不能混用或宣称一致 |

第三行来自已有的[模型诊断记录](../results/fetruth-model-diagnostics.json)，不是本轮新产生的项目建议数。论文归档的 16 条也不是确认的 16 个缺陷，更不是当前项目中的 16 个缺陷。

本轮复用未变化的论文归档推理证据，重新核对保存的两份建议集合；新增运行的是当前项目 Java 示例。归档推理成功说明该固定材料可重放，较新源码流程的模型差异仍是 feTruth 用于正式评测前需要处理的问题。

本次项目建议为：

~~~text
源方法：
com.example.OrderService::createOrder(java.lang.String, double, int):java.lang.String

建议目标类：
com.example.PaymentService
~~~

目前没有移动这个方法。它承担订单流程，是否应移到支付类需要核对职责、异常传播和库存行为。直接按模型输出修改，会把“模型给出的候选”错误地当成“已确认的设计缺陷”。

### 4.3 怎样接入项目

原 JAR 负责解析 Java 和提取特征；原 Python 程序负责模型推理。新增包装脚本只准备隔离目录、启动程序、保存日志和结果。适配器读取原始 TSV 与 features.json，确认推荐确实对应已提取的候选，再创建：

~~~text
Java 类节点
  └── OBSERVED_BY → Feature Envy 候选
                      ├── 完整方法签名
                      ├── 目标类
                      ├── 模型摘要、阈值和工作流
                      └── 原始 TSV、特征及运行记录
~~~

额外记录候选覆盖数。没有提取出候选时脚本报错，避免把“解析失败或没有覆盖”解释成“代码没有问题”。当前示例只产生一个候选，不代表四个类的每个方法都做了完整设计评估。

源码入口为 [run_fetruth_project.py](../scripts/run_fetruth_project.py)，论文归档重放为 [replay_fetruth_artifact.py](../scripts/replay_fetruth_artifact.py)。完整项目结果见[本次目录](../results/fetruth-project/20261028-142453-172415/summary.json)。

## 5. Kivi：配置各自合法，放在一起却可能出问题

### 5.1 先理解它检查什么

Kubernetes 把应用实例运行在 Pod 中，节点提供 CPU 和内存。Deployment 管理期望副本数，HPA 根据负载调整副本数，调度器决定每个 Pod 放到哪个节点。

假设要求“任意时刻新增的 Pod 都有可放置节点”。这就是一条待验证的性质。Kivi 把相关配置、集群拓扑、控制器行为和事件整理成模型，再让 SPIN 检查模型中的执行路径：

~~~text
应用 YAML + 节点与初始 Pod 状态 + 待检查性质
                 ↓
          Kivi 生成 Promela 模型
                 ↓
         SPIN 探索可能的状态变化
                 ↓
      找到反例，或完成本次范围内的检查
~~~

Promela 是 SPIN 使用的建模语言。反例不是一句“配置有风险”，而是一条能导致性质不成立的步骤序列。比如“初始有 5 个 Pod → HPA 请求第 6 个 → 每个节点都被某条约束排除”。

论文还使用逐步扩大规模的策略减少验证成本。本文复现采用固定拓扑参数 -o，没有复现全部规模探索实验，也不把小规模验证当成对任意集群规模的保证。[论文与作者材料](https://www.usenix.org/conference/atc24/presentation/liu-bingzhe)、[源码](https://github.com/bingzheliu/Kivi)。

### 5.2 复现的 C3 案例，可以手工算出来

三个节点分属两个 zone。zone 可以理解为部署分区。已有 5 个 Pod，一种分布如下：

| 分区 | 节点 | 已有 Pod 数 |
| --- | --- | ---: |
| A | node-1 | 2 |
| A | node-2 | 1 |
| B | node-3 | 2 |

配置同时要求：

- 按节点分散：最多的节点和最少的节点，Pod 数相差不超过 1。
- 按 zone 分散：最多的 zone 和最少的 zone，Pod 总数相差不超过 1。
- 两条规则都是硬约束，不能满足时不调度。
- HPA 最多允许扩到 6 个副本。

5 个副本时，节点数为 2、1、2，差值是 1；zone 总数为 3、2，差值也是 1，两条规则都满足。

现在增加第 6 个：

| 新 Pod 尝试放置位置 | 会发生什么 |
| --- | --- |
| A 分区的任一节点 | A/B 的总数变成 4/2，zone 差值为 2，违反 zone 规则 |
| B 分区唯一节点 | 节点数变成 2/1/3，节点差值为 2，违反节点规则 |

所以不是“没有填写某个必要字段”，也不是“机器完全没有资源”，而是两条放置要求在这次扩容时无法同时满足。

本次修改仅将 zone 规则的 maxSkew 从 1 改为 2。节点规则仍为 1，HPA 最大副本仍为 6，检查的性质仍为 Pod 可调度。这样可以把第 6 个 Pod 放到 node-2，节点分布为 2/2/2，zone 分布为 4/2。

这个修改允许 zone 之间多一个副本差距，是可用性与分布均衡之间的一项选择。如果业务必须维持更严格的跨 zone 容灾要求，应该调整拓扑等条件，不能无条件采用这个修改。

### 5.4 环境问题与复现边界

Windows 不接受作者部分日志文件名中的冒号。因此用 Git 保存源码对象并生成 tar，在 Linux 容器中解包运行，没有删除作者案例后假装完整检出。

另一个实际问题是 SPIN 版本。Debian 自带的 6.5.2 标注日期为 2019 年，运行作者模型时出现数组参数语法错误。改用固定提交 090f742 的 SPIN 源码编译后成功；它也显示 6.5.2，但日期为 2025-09-18。只记录“SPIN 6.5.2”不足以重建本次环境。

包装程序还显式检查 SPIN 和编译器的退出码。原辅助函数可能吞掉进程错误，不能把“调用完成”当成“模型通过”。新增程序保存原始输出，并拒绝不完整搜索、深度耗尽和基础设施错误；没有修改 Kivi 的判断算法。

本次验证对象是模型。没有在真实 K8s 上制造 C3 故障。作者解析器只覆盖部分 K8s 功能，不能假设多容器、亲和性、污点、资源精度和所有控制器语义都被完整表示。真实集群接入还需要把对象映射到该模型，并核对模型与实际行为是否一致。

## 6. Reynard：让服务在出错条件下接受同一套业务检查

### 6.1 它怎样产生故障测试

Reynard 在服务通信路径上使用代理，观察一次请求实际经过哪些服务，再在后续执行中改变指定调用的结果。测试程序发起业务请求，并检查最终返回值或业务状态。

这里的 trace 是一次请求的调用记录。它用于确认故障确实发生在指定链路，也用于理解下游变化如何传到上游。仅有“请求注入成功”的控制接口返回值还不够，必须核对代理记录中的实际故障。

Reynard 的 Service Encapsulation Reduction，简称 SER，根据子服务已经表现出的对外行为，减少部分重复故障组合探索。关掉 SER 时，其他已有约简仍然存在，所以不能把该配置写成“完全无优化的全穷举”。[论文及正式发表页](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/151/Automated-Network-Level-Fault-Injection-Testing-of-Microservice-Architectures)。

### 6.2 原始案例复现

固定 v0.2.2-artifact，提交 7fc79c85f5eefd766946a6d878abd441f7641f81。原 patterns 场景的已有运行证据如下：

| 设置 | JUnit 执行数 | failures | errors | skipped |
| --- | ---: | ---: | ---: | ---: |
| SER 关闭 | 1,849 | 0 | 0 | 0 |
| SER 开启 | 543 | 0 | 0 | 0 |

执行数量减少 (1849−543)/1849 = 70.6328%。这是本场景的执行数量变化，不是所有系统的性能提升，也不是本轮重新测出的耗时结论。相关源码、镜像和测试未变化，按验证策略复用已保存的有效结果，汇总脚本重新核对原始 JUnit。

### 6.3 为修复正确性加入业务契约

当前新增场景使用作者实验系统中的 frontend → recommendations 调用。推荐是可选功能，固定业务规则为：

- 推荐服务正常时，frontend 返回 200 和 ["product-1"]。
- 推荐服务返回错误时，frontend 仍返回 200，推荐列表为 []。
- 修改前后使用同样的请求、故障类型和断言。

修改是启用场景已有的空列表降级行为。没有通过放宽断言让测试过关。

| 下游情况 | 修改前 frontend 结果 | 修改后 frontend 结果 | 契约判定 |
| --- | --- | --- | --- |
| 正常 | 200，["product-1"] | 200，["product-1"] | 前后通过 |
| 注入 HTTP 500 | 500 | 200，[] | 失败 → 通过 |
| 注入 HTTP 502 | 500 | 200，[] | 失败 → 通过 |
| 注入 HTTP 503 | 500 | 200，[] | 失败 → 通过 |
| 注入 HTTP 504 | 500 | 200，[] | 失败 → 通过 |

前后各执行 5 次，失败数从 4 变成 0，errors 和 skipped 均为 0。每次记录包含实际故障、trace、HTTP 状态码、返回内容和契约结果。输入故障集合前后一致，健康控制也通过。

四种错误状态暴露的是同一个降级缺口，不是四个独立缺陷。HTTP 504 响应也不等于真实 TCP 超时；网络断连、真实延迟、TLS、异步消息链路需要另设实验。

结果见[契约实验](../results/reynard-contract/20261028-125509-168163/summary.json)，判定代码见 [MaturityContractIT.java](../baselines/fixtures/reynard/MaturityContractIT.java)。当前尚未把这组场景移到团队自己的 otel-demo 原型。

### 7.2 不同状态保留不同含义

| 状态 | 含义 | 后续能否直接宣称修复成功 |
| --- | --- | --- |
| candidate | feTruth 提出的待核实建议 | 不能，需要确认问题及行为测试 |
| fail | 指定性质或业务契约失败 | 是问题证据，仍需结合检查范围 |
| pass | 本次指定检查通过 | 只能说明该检查通过 |
| measured | 覆盖数等统计记录 | 不是成功或失败 |
| error | 工具或证据处理失败 | 不能作为通过 |
| not-observed-after | 修改后没有对应观察 | 不能当成问题消失即修复 |

比较时保持对象键、性质或故障集合稳定。这样“同一条检查从 fail 到 pass”和“原来那条检查没执行”不会混为一谈。

### 7.4 如何挂到团队已有节点

已有图谱节点应通过明确映射复用，不能因为名称相近就自动合并。适配器支持对象键到现有节点的绑定：

| baseline 对象键 | 可以绑定的节点 |
| --- | --- |
| java:完整类名 | Module 或 Service |
| k8s:集群/namespace/资源类型/资源名 | Deployment |
| service:服务名 | Service |

绑定前检查节点存在、类型合适、图谱 namespace 一致。这里图谱 namespace 是项目身份，与 Kubernetes namespace 不是同一个概念。

Kivi C3 模型中的 php-apache 与当前真实 kind 集群里的 audit-demo 不是同一对象，本轮没有将它们强行绑定。自动读取实时集群并生成 Kivi 模型的转换器尚未完成。

## 8. 后续 benchmark 怎样使用这三个方法

一个评测样例至少包括输入版本、问题真值、允许的行为、baseline 输出、候选修改和修改后的独立判定。真值表示由样例设计或人工确认的问题，不能直接用工具自己的输出给自己打分。

| 部分 | 适合构造的样例 | 基线输出 | 修改后应额外检查 |
| --- | --- | --- | --- |
| Java 设计 | 一个已确认职责不合理的方法，同时准备相似但合理的编排方法 | 方法/目标类候选 | 原有测试通过；依赖方向、职责和公开接口符合预期 |
| K8s 部署 | 拓扑分布规则与扩容冲突；一个没有冲突的对照 | 反例或指定范围的通过 | 同一性质通过；真实集群扩容观察；可用区分布要求未被偷偷取消 |
| 微服务运行 | 可选推荐服务失效；关键支付服务失效 | 注入轨迹与业务断言结果 | 可选功能可以降级；关键操作满足失败策略及状态不变量 |

衡量诊断质量时，确认的真阳性数除以所有报告数是精确率；确认的已知问题中被发现的比例是召回率。两者都需要独立标注和匹配口径。当前项目示例很小，Kivi 只复现了 C3，Reynard 只覆盖给定契约，因此本次不报告项目级精确率、召回率或总体成熟度提升百分比。

对自动优化，建议保存完整链条：问题证据 → 修改差异 → 原判定重新执行 → 相关健康行为检查。feTruth 提供候选位置；Kivi 和 Reynard 各自在自己的范围内提供修改对照。三者都不能代替完整的业务正确性证明。
