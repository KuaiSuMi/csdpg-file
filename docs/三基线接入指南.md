# 从零运行：feTruth、Kivi、Reynard

历史实验说明：本文保留旧 feTruth/Kivi/Reynard 流程。当前学术基线为 **Infer/Pulse + feTruth**，请使用[最新学术指南](两项学术基线复现.md)和[当前选型](学术基线复审结论.md)。

AppCAT 和 NeuVector 已加入同一个图谱构建入口，分别使用 `--appcat` 和 `--neuvector`；后者同时需要 `--cluster`。两项商业结果的输入格式、导入命令和对象绑定写在商用基线复现文档第 4 节。下文保留三项学术基线的操作步骤。

本文对应 2026 年 10 月 28 日选定的三项会议基线。方法解释和选型比较见[调研报告](三基线选型与复现.md)。



命令使用 Windows PowerShell。文件名后的一长串提交号用于固定源码版本；结果目录中的数字是运行时间。每条命令都在本交付根目录执行，除非明确写了其他目录。

建议按下面顺序操作：

1. 先用已保存结果生成图谱，理解输入输出，不启动全部实验。
2. 选一个 baseline 重跑，查看它的原始结果。
3. 再把同一种输入替换成团队项目，补上对象映射和业务判定。

只想阅读结果，可以直接打开[汇总](../results/selected-conference/summary.json)，不用安装运行环境。

compare_baseline_graphs.py 的两个图谱路径是位置参数，不加 --before 或 --after。

~~~json
{"check-passed-after": 5, "unchanged": 2}
~~~

它表示 Kivi 的 1 条性质、Reynard 的 4 个故障情形通过了修改后检查；feTruth 候选和健康请求的状态不变。不要把 5 当作五个独立漏洞，也不要把它除以图谱节点数计算成熟度。

三个输入参数的目录结构不同：

| 参数 | 应传什么 | 里面至少需要什么 |
| --- | --- | --- |
| --fetruth | 一次项目源码运行的根目录 | recommendations.tsv、features.json、summary.json |
| --kivi | 一次 Kivi 运行中的 before 或 after 子目录 | processes.json、原始进程输出、kivi.log、model-input.json、result.json |
| --reynard | 一次业务契约实验中的 before 或 after 子目录 | junit.xml、observations/*.json |

feTruth 论文归档目录、Reynard SER 原始实验目录都不能直接冒充对应参数输入；它们没有相同的覆盖和业务观测记录。

## 3. feTruth：先重放论文，再运行本项目源码

### 3.1 准备工具源码、JDK 和模型文件

feTruth 项目包装脚本目前使用固定路径 .runtime/jdk17/jdk-17.0.20.1+1/bin/java.exe。将对应 [Temurin 17 发布包](https://github.com/adoptium/temurin17-binaries/releases/tag/jdk-17.0.20.1%2B1)解压到该位置。Reynard 的脚本则允许用参数指定其他 JDK 路径。

两个数组各约 485 MB，需预留下载包、解压文件和容器空间。项目脚本通过硬链接复用数组，要求 .runtime 下这些目录在同一磁盘卷。

## 4. Kivi：用原模型重现调度冲突

### 4.1 为什么在 Linux 容器中准备

作者仓库包含 Windows 不能直接检出的文件名。使用 --no-checkout 获取 Git 对象，再把指定提交导出成 tar。tar 在 Linux 镜像中展开，作者文件得以保留。

新机器执行：

~~~powershell
New-Item -ItemType Directory -Force .runtime/kivi-build | Out-Null
git clone --no-checkout https://github.com/bingzheliu/Kivi.git baselines/sources/kivi
if ($LASTEXITCODE -ne 0) { throw 'Kivi Git 对象下载失败' }
$SourceTar = Join-Path (Get-Location).Path '.runtime/kivi-build/source.tar'
git -C baselines/sources/kivi -c core.protectNTFS=false archive --format=tar "--output=$SourceTar" 81e6c253573b0cc41727885948c1240892d1a6e2
if ($LASTEXITCODE -ne 0) { throw 'Kivi 源码归档失败' }

git clone https://github.com/nimble-code/Spin.git .runtime/Spin
if ($LASTEXITCODE -ne 0) { throw 'SPIN 源码下载失败' }
$SpinTar = Join-Path (Get-Location).Path '.runtime/kivi-build/spin.tar'
git -C .runtime/Spin archive --format=tar "--output=$SpinTar" 090f74209025a53297990ec17deca1bd51cb92a5
if ($LASTEXITCODE -ne 0) { throw 'SPIN 源码归档失败' }

docker build -t maturity-kivi:atc2024 -f baselines/kivi/Dockerfile .runtime/kivi-build
if ($LASTEXITCODE -ne 0) { throw 'Kivi 镜像构建失败' }
~~~

core.protectNTFS=false 仅作用于这次 archive 命令，没有写入全局 Git 配置，也没有把非法路径检出到 Windows。

Dockerfile 使用固定 Python 基础镜像、作者 requirements.txt 和固定 SPIN 源码。Dockerfile 前一层安装的发行版 SPIN 最终被源码构建替换，实际调用的是 /opt/kivi/libs/Spin/Src/spin。不要把系统包的同名版本当成相同二进制。

本次最终镜像 ID 为：

~~~text
sha256:890f3ff7676bc5e6b0a0e891d91114164ed21185fac556e7606308c72216893b
~~~

构建仍会解析 Debian 包和编译工具，新机器镜像 ID 可能不同，应保存实际 ID 与日志；不要把重新构建宣称为字节完全一致。

### 4.2 一条命令运行四组实验

~~~powershell
& $Python scripts/run_kivi.py
~~~

它会创建 results/kivi/时间戳，并依次运行：

1. paper-violation：作者 C3 违规模型。
2. paper-control：作者 -cn 对照模型。
3. before：从作者 YAML 读入的原配置。
4. after：zone maxSkew 改为 2 的配置。

预期结果依次为 fail、pass、fail、pass。fail 在这里表示发现预期的调度反例；外层脚本若成功完成整个实验，退出码仍为 0。编译失败、超时、证据缺失则会终止，不能记成调度问题。

也可以指定一个尚不存在的输出目录：

~~~powershell
& $Python scripts/run_kivi.py --output out/kivi-repeat
~~~

已存在目录会被拒绝，以免混入旧日志。这里没有 --input 或 --cluster 参数，当前包装脚本专门复现 C3，不能假装它已经支持任意集群自动采集。

### 4.3 看懂输出

~~~text
results/kivi/某次运行/
├── inputs/before/           原作者配置
├── inputs/after/            修改后的配置
├── repair.patch             配置差异
├── paper-violation/         作者违规模型结果
├── paper-control/           作者对照模型结果
├── before/                  原 YAML 的模型检查结果
├── after/                   修改 YAML 后的模型检查结果
└── summary.json
~~~

每个阶段里的重要文件：

| 文件 | 用途 |
| --- | --- |
| command.json | 实际 Docker 命令和 Kivi 参数 |
| processes.json | 生成、编译、运行验证器的命令及退出码 |
| process-*.stdout.txt / stderr.txt | 原始进程输出 |
| kivi.log | 待检查性质、验证进度和反例回放 |
| model-input.json | 送入模型构造的实际对象 |
| model/ 下的 .pml | Kivi 生成的 Promela 模型 |
| result.json | 根据原始输出整理出的本组结果 |

原始输入由 yaml/deploy.yaml、yaml/autoscaler.yaml、user_input/cluster_configs.json、user_input/intents.json 组成。它不仅需要 Deployment YAML，还需要节点、初始 Pod 分布和性质。

例如 before 中搜索 No feasible node 可以看到反例；after 的验证器输出应包含 errors: 0，且不能出现搜索未完成或深度耗尽。适配器会检查这些条件，不只读取 result.json 里手填的 pass。

### 4.4 替换成实际 K8s 时的工作

先采集目标 Deployment、HPA、节点标签、资源和当前 Pod 分布，再确认作者解析器对这些字段的支持。缺少模型支持的字段需要明确列出，不能静默丢弃后仍称“实际集群通过”。

随后应在与实际配置对应的模型中运行同一性质，再在隔离集群中执行实际扩容，核对模型反例和真实事件。最后给结果绑定真实集群、K8s namespace、资源类型和资源名。

这一转换与实集群验证尚未实现。当前结果的 source_type 为 document，明确表示来自配置及模型；不会标成真实 deployment 采样。

### 5.2 运行业务契约的修改前后对照

~~~powershell
& $Python scripts/run_reynard_contract.py --java-home $JavaHome --maven $Maven
~~~

脚本创建 results/reynard-contract/时间戳，先禁用空列表降级，再启用降级。两组请求、故障和业务断言相同。测试文件临时放入作者测试目录，完成后清理本脚本创建的文件。

成功输出应显示：

~~~text
before: tests=5, failures=4, errors=0, skipped=0
after:  tests=5, failures=0, errors=0, skipped=0
~~~

修改前 Maven 因业务断言失败返回非零是预期的，外层脚本会检查 JUnit 和健康控制。若 errors 非零、没有 JUnit 或健康请求失败，就是环境或场景问题，不能当成成功发现降级缺陷。

每个阶段都有 junit.xml、maven.log、observations/*.json。observation 中的 faultload 是请求注入的故障，trace.reports 中的 injected_fault 是代理实际注入的故障；适配器要求两者一致。

### 5.3 重跑原始 SER 对照

本次已复用有效结果，只有环境或场景变化时才需要重新跑。用新的根目录避免覆盖旧证据：

## 6. 把观察挂到已有项目节点

### 6.1 先确认对应的是同一个对象

命令行的 --base-graph 读取已有图谱，--bindings 读取一个 JSON 映射。映射左边是 baseline 对象键，右边是已有节点 ID。

  "service:frontend": "从已有图谱复制的实际服务节点ID"
}
~~~

这是格式示例，右边占位文字必须替换后才能执行。可以先检查图谱中的对象：

~~~powershell
$Base = Get-Content out/project.kg.json -Raw -Encoding UTF8 | ConvertFrom-Json
$Base.nodes | Where-Object { $_.type -in @('Module', 'Service', 'Deployment') } | Select-Object id, type, name, namespace
~~~

不要根据名字相似直接绑定。当前 Kivi 的对象是 k8s:kivi-c3/default/Deployment/php-apache，不能绑定到另一个集群的 audit-demo。

填好 out/bindings.json 后，以下命令将 Java 观察合并到已有图谱。--namespace 必须替换为原图谱对应项目的实际值：

对不存在的节点、不同项目 namespace 或错误类型，程序会报错。Java 观察允许绑定 Module/Service，Kivi 绑定 Deployment，Reynard 绑定 Service。

### 6.2 在项目 Python 入口中使用

先让当前 Python 能找到 integration：

~~~powershell
$env:PYTHONPATH = (Resolve-Path integration).Path
~~~

下面示例只处理一份 Kivi 结果，使用项目原流水线：

~~~python
from pathlib import Path
from kg_builder import BuildPipeline, BuildSettings
from kg_builder.graph.serialization import save_graph
from maturity_baselines import BaselineCollector

settings = BuildSettings(
    repo_path=Path.cwd(),
    output_path=Path("out/kivi-only.kg.json"),
    namespace="baseline-validation",
    enrich=False,
)
collector = BaselineCollector(
    "kivi",
    "results/kivi/20261028-143054-347369/after",
    namespace=settings.namespace,
)
report = BuildPipeline(settings).run(collectors=[collector], write_outputs=False)
if report.warnings:
    raise RuntimeError("; ".join(report.warnings))
report.graph.meta["baseline_runs"] = {
    result.collector: result.metrics for result in report.results
}
save_graph(report.graph, settings.output_path)
print(report.graph.stats())
~~~

在现有项目入口中，把 BaselineCollector 加入已有采集器列表即可。Python 的 bindings 参数传“对象键 → KGNode 对象”，命令行的 JSON 传“对象键 → 节点 ID”，由命令行程序负责查找。

enrich=False 让此示例只演示采集和构图，没有启动完整 SCIP、Joern 或 LLM 流程。

## 7. 把最小案例移到团队 otel-demo

按三个独立入口迁移，比先安装所有组件更容易定位问题。

| 入口 | 第一份应准备的真实输入 | 第一个验收条件 |
| --- | --- | --- |
| Java | 一个固定提交的 Java 服务目录 | 能提取非空候选；结果定位到实际类和方法 |
| K8s | 一个目标 Deployment、HPA、节点及 Pod 分布 | 模型表达与真实对象一致；明确哪些字段没建模 |
| 运行故障 | 一条 frontend 到下游的请求及允许返回值 | 健康请求通过；代理轨迹证明确实拦截目标调用 |

Reynard 的 Compose converter 可以作为部署接入入口，但生成文件仍要按实际服务核对。对真实 Compose 文件运行作者工具后，检查地址替换、端口和追踪传播，再编写业务契约。当前团队部署文件尚未提供，未生成对应补丁。

FaaS 也不能只写“支持 Kubernetes”就算完成。Knative 的 Revision、Route、冷启动和缩容到零，与 OpenFaaS 的函数规格、网关和扩缩容标签不同。先确定平台，再定义函数身份、采集字段和业务断言；本次三项工具没有经过 FaaS 实验。

## 8. 遇到问题先看哪里

| 现象 | 先检查 | 处理方向 |
| --- | --- | --- |
| No module named kg_builder | 是否使用 $Python 对应环境 | 在同一环境按 1.2 安装项目 |
| feTruth 容器不存在或未运行 | docker ps -a 中的名称、挂载目录 | 首次创建，或启动已有正确容器 |
| feTruth 缺词向量文件 | word2vec 三个文件是否齐全 | 下载两个数组并复制索引文件 |
| feTruth 输出与归档不同 | 使用的是归档 evaluate.py 还是较新源码流程 | 分开版本和输入，不混报结果 |
| Java 候选为空 | extraction.log、Java 版本、源码目录 | 先解决提取范围，不作“无问题”结论 |
| Kivi Git checkout 非法文件名 | 是否误用了普通 checkout | 使用 4.1 的无检出归档流程 |
| SPIN 出现 missing array index | 实际 SPIN 编译提交和日期 | 用固定源码构建；不能只比较 6.5.2 版本号 |
| Kivi 没有完整验证输出 | processes.json、stderr 和 kivi.log | 区分编译错误、超时和真正反例 |
| Reynard 修改前 Maven 失败 | JUnit failures/errors/skipped 与健康控制 | 判断是否为预期业务失败 |
| Reynard 没有 junit.xml | maven.log 最早的错误 | 修复构建或启动问题后再测试 |
| 图谱说证据不一致 | 原始输出是否被改写或混入其他运行 | 找到同一次运行的完整材料 |
| 修改后观察缺失 | 输入范围、规则及场景是否仍执行 | 缺失不是通过，补齐覆盖再比较 |

本机代表性实验、图谱生成和针对性检查已完成；第二台干净机器尚未从头重装验证。新环境应保存实际依赖解析、镜像 ID 和输出，尤其注意旧 TensorFlow wheel、SPIN 编译版本及 Docker 网络。
